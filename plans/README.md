## Dependency notes

- **003 は 002 の後**: 空 facts フォールバックの挙動を固定するテスト(002)がある状態で collector を動かす(003)。
- **007 は 002 の後**: パースキャッシュは「パース失敗時に何が起きるか」の契約(002 が固定)を保存しなければならない。
- 005 と 008 は相互作用あり(実行順は不問): config ファイルのローダー機構の選択肢(native TS import)は Node フロアの決定に依存する。008 の設計書は 005 の結論(`>=22.12.0`)を前提としてよい。
- 004 の AGENTS.md には現行規約を書く。以降の計画で規約を変える場合は AGENTS.md も更新すること。
- **010 → 011 は直列**: 010(実装)のマージ後にのみ 011(docs)を実行する — docs は出荷済みの実挙動を Step 1 で実測してから書く設計。両計画の正は Accepted 済み設計書 `docs/superpowers/specs/2026-07-05-config-file-design.md`(vitest が in-process の dynamic import を変換するため .ts の floor エラー経路は子プロセスでしか検査できない、という spike の発見を含む)。

## Findings considered and rejected

監査で検出したが計画化しなかった所見(再監査防止のための記録):

- **DEBT-02**(HeadTag 抽出の cli/vite 二重実装): 実在する M 工数のドリフトリスクだが、今回の選択から外れた。将来モード間のスコア不一致が報告されたら最有力容疑。
- **PERF-02 / DEBT-03**(ルートパスとコンポーネントパスの二重パース、core 抽出の未完): L 工数・MED リスク。007 のキャッシュで最大の無駄は解消される。着手するなら characterization テスト拡充後。
- **DEBT-04**(`rules/perf/` と `rules/performance/` の並立): S だが機能コストほぼゼロ。次にルール整理をする際のついで作業として推奨。
- **DEBT-05**(`rules/index.ts` の46ルール×3回列挙): 同上。TS が漏れを検知するため実害は小さい。
- **TEST-02**(`--min-health` 検証の bin.ts/index.ts 重複): 軽微。bin.ts 側のコピーを削って `run()` の検証に一本化するだけの小掃除。
- **DX-02**(pre-commit フック・`.editorconfig` なし): ソロメンテナー + 高速 CI では価値薄と判断し見送り。
- **DOCS-01**(health-report ガイドの「設定可能な重み」): 008 の config ファイル実装で根本解決する方針のため、単独の文言修正計画は作らなかった(実装まで時間が空くなら暫定の文言弱めも可 — 008 の Maintenance notes 参照)。
- **依存監査**: `pnpm audit --prod` は moderate 1件のみ(docs ツールチェーン経由の `yaml`、実行時到達性なし、Renovate 対応圏内)。対応不要。
- **a11y カテゴリ再導入 / トレンド履歴機能**: 設計ドキュメントで明示的に廃止・non-goal とされた決定済み事項。提案しない。

# Design: SEO head completeness + robots correctness (sub-project A)

Strengthens svelte-vitals' SEO coverage toward parity with the static, head/markup-decidable perspectives of the popular **claude-seo** skill suite. (claude-seo is an AI-agent SEO suite whose backlinks/rankings/keyword/competitor/content-generation/CWV/crawl capabilities are runtime/web-data driven and out of svelte-vitals' static-analysis scope; this targets only the perspectives a source/rendered-`<head>` analyzer can own.)

This is **sub-project A** of a 3-phase SEO-strengthening effort:

- **A (this spec)** — head-completeness presence rules + robots/indexability correctness. Mostly the existing `headTagRule`/project-rule patterns, plus two small targeted captures.
- **B (later)** — title/meta-description **length** rules; needs capturing the literal text value of those tags (only checkable for static values).
- **C (later)** — **JSON-LD validation** beyond SEO008's presence; needs capturing + parsing the literal JSON-LD `<script>` content.

B and C each require a distinct capture extension (literal text; literal JSON) and are their own spec → plan → implementation cycles.

## Goal

Add six new SEO rules decidable from the resolved `<head>` and project facts, before deploy, without a browser or web data:

| ID         | Check                                                                                                             | Severity          | Shape                          |
| ---------- | ----------------------------------------------------------------------------------------------------------------- | ----------------- | ------------------------------ |
| **SEO010** | **Indexability** — a route whose `<meta name="robots">` content statically contains `noindex`                     | `info` (advisory) | flag-on-presence (custom rule) |
| **SEO011** | **Twitter Card** — `<meta name="twitter:card">` present                                                           | `info`            | `headTagRule`                  |
| **SEO012** | **Open Graph description** — `<meta property="og:description">` present                                           | `warning`         | `headTagRule`                  |
| **SEO013** | **Open Graph URL** — `<meta property="og:url">` present                                                           | `info`            | `headTagRule`                  |
| **SEO014** | **Viewport** — `<meta name="viewport">` present                                                                   | `warning`         | `headTagRule`                  |
| **SEO015** | **Sitemap referenced in robots.txt** — when robots.txt and a sitemap both exist, robots.txt has a `Sitemap:` line | `info`            | project rule                   |

Severity rationale: SEO012 (og:description) and SEO014 (viewport) are `warning` — og:description parallels og:title (SEO005, `warning`); viewport matters for mobile-first indexing. SEO010/SEO011/SEO013/SEO015 are `info` — noindex may be intentional (can't know statically), Twitter falls back to Open Graph, og:url is usually covered by the canonical, and a sitemap can also be submitted via Search Console.

## SEO010 — Indexability (the headline rule)

Unlike every other SEO rule (which penalizes the _absence_ of a desired tag), SEO010 surfaces the _presence_ of a `noindex` directive — an accidental `noindex` silently deindexes a page (highest-impact SEO bug). Because static analysis cannot know whether a `noindex` is intentional (`/admin`, thank-you pages), it is an **`info` advisory**: it surfaces the route with a "verify this is intentional" message, never fails the default CI gate (`--fail-on=critical`), and has minimal score impact. A dynamically-bound `content={x}` is **never** flagged (no false negatives) — only a statically-resolvable `noindex` token.

## Data model & provider changes (minimal, both modes)

- **`HeadTag.noindex?: boolean`** (core `head.ts`) — set on a `<meta name="robots">` tag when its `content` statically contains the `noindex` token; `undefined` when the content is dynamic or the token is absent. Mirrors the targeted `as`/`hasCrossorigin` captures already added for PERF003/004.
  - CLI (`parse.ts`): read the robots meta's `content` via `attrText`; `noindex: /(^|,|\s)noindex(\s|,|$)/i.test(content)` when literal. A dynamic `content={x}` yields no literal → `noindex` unset → not flagged.
  - vite (`parse-html.ts`): `content = meta.getAttribute('content')`; same token test.
- **`Project.robotsReferencesSitemap?: boolean`** (core `types.ts`) — whether the **static** `static/robots.txt` file contains a `Sitemap:` line. Set only when robots.txt is that static file; left **`undefined`** when robots.txt is a `+server` endpoint (`ROBOTS_SOURCE_PATHS` also lists `src/routes/robots.txt/+server.{ts,js}`) — its output is generated by code, so a `Sitemap:` reference can't be determined statically and must not be guessed (no false positives). Also `undefined` when robots.txt is absent or unreadable.
  - CLI (`collectProjectFacts`): if `static/robots.txt` exists, read it via the runtime and test `/^\s*sitemap:/im`; otherwise leave `undefined`.
  - vite (`collectRenderedProject`): same, reading the static file with `node:fs`.
- **SEO011–014** need **no model change** — they are new `headTagRule` instances matching by `name`/`property`.

The `ROBOTS_SOURCE_PATHS` list already drives existence detection; the content read reuses the first existing path.

## Rules (core, pure functions)

- **SEO011–SEO014**: `headTagRule({ match, label, severity, recommendation, rationale, fix })`, matching `t.kind === 'meta' && t.name === 'twitter:card'` / `t.property === 'og:description'` / `t.property === 'og:url'` / `t.name === 'viewport'`. Each emits the standard missing/empty/present result per route, exactly like SEO002/SEO004/SEO005.
- **SEO010**: a custom route-scoped rule that scans `ctx.heads`; for each head with a robots meta where `noindex === true`, emit one `info` finding (`detection: { presence: 'own', value: 'static' }`) with a "verify intentional" message. Routes without a static `noindex` emit nothing (no penalty). No `fix` snippet that "removes" code — the recommendation explains how to drop `noindex` if unintended.
- **SEO015**: a project-scoped rule (mirrors SEO006/SEO007 in `project-rules.ts`): when `project.hasRobotsTxt && project.hasSitemap && project.robotsReferencesSitemap === false`, emit one `info` finding with a fix (add `Sitemap: https://example.com/sitemap.xml` to robots.txt). When `robotsReferencesSitemap` is `undefined` (couldn't read), emit nothing.

All six are registered in `allRules` (`rules/index.ts`) and exported from the core index; `allRules` consumers (MCP `explain_rule`, scoring, the docs-links test) pick them up dynamically.

## Coverage note (honest)

`<meta name="robots">` and `<meta name="viewport">` commonly live in `app.html`, which the **static (CLI) mode cannot see** (it resolves `<svelte:head>` only); they are covered in **rendered / plugin mode**. og/twitter tags are typically in `<svelte:head>` (covered in both). This mirrors the existing static-vs-rendered coverage split and is documented for users.

## Testing

- **core rule tests** (`packages/core/test/seo-head-completeness.test.ts`): SEO010 flags a head with `noindex:true`, ignores `noindex:undefined` (dynamic/absent) and `index,follow`; SEO011–014 flag missing / pass present (one `headTagRule` assertion each); SEO015 flags `hasRobotsTxt && hasSitemap && robotsReferencesSitemap:false`, passes when `true`, emits nothing when `undefined` or when robots/sitemap absent.
- **provider extraction tests**: CLI `parse.ts` — `<meta name="robots" content="noindex,follow">` → `noindex:true`; `content={x}` → `noindex` unset. vite `parse-html.ts` — same from rendered HTML. CLI `collectProjectFacts` + vite `collectRenderedProject` — a robots.txt with a `Sitemap:` line → `robotsReferencesSitemap:true`; without → `false`.
- **docs link integrity**: `packages/cli/test/docs-links.test.ts` asserts every SEO/PERF rule has en + ja pages — SEO010–SEO015 pages must exist (part of this increment).

## Documentation

Rule reference pages `docs/src/content/docs/rules/seo0{10..15}.md` + their `ja/` counterparts (matching the existing SEO page template: title, severity, what it checks, why it matters, how to fix with a snippet). No guide changes.

## Release

`@svelte-vitals/core` + `svelte-vitals` + `@svelte-vitals/vite` + `@svelte-vitals/mcp` **minor** (new findings surface in the CLI, static report, vite plugin/dev UI, and MCP analyze/explain_rule).

## Non-goals / follow-ups

- **Phase B** — title/description length (literal-text capture).
- **Phase C** — JSON-LD validation (literal-JSON capture + parse).
- **Canonical self-reference correctness** — needs URL/origin knowledge; dynamic canonicals can't be checked.
- **H1 uniqueness / heading hierarchy** — needs body-markup parsing (svelte-vitals resolves head + `<img>` only today).
- **hreflang validity** — needs capturing the literal `hreflang`/`href` values; a candidate later phase.
- Everything runtime/web-data driven in claude-seo (backlinks, rankings, keyword/competitor research, content generation, CWV field data, crawl-based checks) — out of svelte-vitals' static-analysis nature by design.
